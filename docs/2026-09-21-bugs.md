# 🔴 優先度：高

### 1. オフラインプレイヤーのショップを削除すると在庫が全消失する

**ファイル:** `managers/ShopManager.java`

これは確定バグやね。

`remove(Shop shop)` で、

* オーナーがオンライン → 在庫 + 資金を返却
* オーナーがオフライン → **資金だけ返却**
* ショップDB行は削除

になってる。

しかもソース内にそのまま、

```java
// 在庫の処理が未実装
//
// オーナーがオフライン
// ↓
// 管理者が /shop remove
// ↓
// DBからショップ削除
// ↓
// 資金は返却
// ↓
// 在庫は消滅
```

と残ってる。

**再現例**

1. Aがショップにダイヤ64個を入れる
2. Aがログアウト
3. 管理者がAのショップを削除
4. ダイヤ64個が永久消滅

### 修正方針

オフライン用の返却キューをDBに保存するのが一番安全やね。

たとえば、

```text
shop_pending_returns
- owner_uuid
- item_data
- amount
```

に保存して、次回ログイン時に返す。

これは**公開サーバーなら最優先**で直したい。

### 2. プレイ時間が短時間ログイン/ログアウトで保存されない可能性

**ファイル:** `managers/PlaytimeManager.java`

`onJoin()` が、

```java
DatabaseManager.executeAsync(
    "INSERT OR IGNORE INTO player_stats ..."
);
```

でレコードを**非同期作成**してる。

一方 `onQuit()` では、

```java
getStoredPlaytimeSeconds(uuid)
```

したあと、

```java
DatabaseManager.executeAsync(
    "UPDATE player_stats SET playtime_seconds = ? ..."
);
```

する。

つまり、

```text
JOIN
 ↓
非同期 INSERT を予約

すぐQUIT
 ↓
SELECT → まだ行がない
 ↓
非同期 UPDATE を予約
```

となり、AsyncScheduler上で

```text
UPDATE
INSERT
```

の順に実行されたら、UPDATEは0行に終わる。

**結果: そのセッションのプレイ時間・last_logoutが消える。**

特に接続直後のキック、接続失敗、再起動などで踏みやすい。

`onJoin()` の初期行作成は同期で `INSERT OR IGNORE` してええと思う。

# 🟠 非同期保存に共通する設計上の問題

ここは個別バグというより、まとめて直した方がええ。

現在 `executeAsync()` を状態保存に使ってる箇所に、

* `PlaytimeManager`
* `MineManager`
* `LandBorderParticleManager`
* `EconomyManager#setHideBalance`

がある。

特に `LandBorderParticleManager` も、

```java
enable()
    → async INSERT OR REPLACE

disableAndForget()
    → async DELETE
```

なので高速に、

```text
ON
OFF
```

すると、タスクが逆転して

```text
DELETE
INSERT
```

になる可能性がある。

するとその場ではOFFなのに、次回ログイン時に**勝手に境界表示が復活**する。

### おすすめ

「最後の値だけが重要」な状態保存は、

```text
1プレイヤー1キーのシリアルキュー
```

まで作るより、この規模ならまず**同期UPDATE**で十分やと思う。

SQLiteアクセス自体は `DatabaseManager` が `synchronized` 化されてるから、以前よりだいぶ安全になってる。

### 24. ショップ資金入力中の取引で残高を巻き戻す可能性

**`ShopListener.java` / `ShopManager.java`**

これも危険。

`requestFunds()` はその時点の古い、

```java
Shop shop
```

を `Pending` に保存する。

その後チャットで金額を入力するまでに別プレイヤーが取引すると、

```text
保存時 funds = 10,000

他プレイヤーが取引
現在 funds = 9,000

店主が5000円出金
```

という状況になる。

でも、

```java
addFunds(s.shop(), -n)
```

は**古い10,000円を基準**に、

```text
10,000 - 5,000 = 5,000
```

をDBへ書く。

本来、

```text
9,000 - 5,000 = 4,000
```

やから、**資金が1000円増殖する**。

逆方向なら消失もあり得る。

これは絶対直した方がええ。

### 25. ショップ価格変更でも古いキャッシュを復活させる

これも `ShopListener`。

チャットで価格入力待ちしてる間に取引が起きると、`Pending` 内の古いShopを使って、

```java
updateSettings(s.shop(), ...)
```

する。

SQL上は価格だけ更新してるけど、そのあとキャッシュに、

```java
old.stock()
old.funds()
```

を含んだShopを再登録してる。

なのでDBは正しいのにメモリだけ、

```text
在庫 100 → 実DB 90
キャッシュ → 100に巻き戻る
```

みたいな状態になり得る。

そのあと取引するとさらに面倒なことになる。

**PendingにはShopそのものじゃなく `shop.id/key` だけ保存して、入力確定時に必ず最新Shopを取得**するのがええ。

### 55. DB transaction API自体が「SQL失敗＝rollback」にならない

**`DatabaseManager.java`**

これは今後のバグ製造機候補。

`transaction()` は、

```java
try {
    action.accept(conn);
    conn.commit();
}
catch (...) {
    rollback();
}
```

になってる。

でも通常の、

```java
DatabaseManager.execute(...)
```

はSQLエラーが起きても例外を外へ投げず、

```java
return -1;
```

する。

つまり、

```java
DatabaseManager.transaction(conn -> {
    DatabaseManager.execute("UPDATE A ..."); // 成功
    DatabaseManager.execute("UPDATE B ..."); // SQLエラー → -1
});
```

だと、

**transaction側はエラーに気付かずCOMMITする。**

現在の重要な処理では、

```java
if (affected < 0) {
    throw new IllegalStateException(...);
}
```

や `require(...)` を入れてる箇所が多いから、既にかなり対策されてる。

でもAPIの契約として危ない。

おすすめはトランザクション内専用で、

```java
executeOrThrow(Connection conn, ...)
```

を使わせること。
