# プレイヤーショップ（チェストショップ）設計

## 概要

QuickShopHikariのようなチェスト設置型のプレイヤーショップ機能を追加する。プレイヤーはチェストをSneak+右クリックすることで「売る/買う」ショップ化でき、他のプレイヤーはそのチェストを右クリックして確認GUI経由でアイテムを売買する。既存の`/lock`（`ContainerLockManager`）に保護を委譲し、荒らし対策・ラージチェスト対策を専用実装で補う。

在庫と資金はチェストの実際の中身とは連動しない**仮想在庫方式**を採用する。チェストは「取引の入口」としての役割のみを持ち、実際の数量はDBで管理する。

## 全体フロー

### ① ショップの設置

1. プレイヤーが`minecraft:chest`を設置する（バニラ通り、特別な操作は不要）。
2. 売買したいアイテムを手に持ち、そのチェストに向かって**Sneak+右クリック**する。
3. 対象ブロックが以下のいずれかに該当する場合は作成を拒否する。
   - `Material.CHEST`以外（トラップチェスト・バレル・シュルカーボックスは非対応）
   - 既にラージチェスト化している（`Chest.Type != SINGLE`）
   - 既に他人が`/lock`でロック済み
   - 設置者のショップ数が上限（`shop.max-per-player`、デフォルト10）に達している
   - 設置者の残高が作成費（`shop.creation-cost`、デフォルト500）に満たない
4. チャットで「BUY（自分が売る）」か「SELL（自分が買い取る）」かを選択させる。
5. 続けてチャットで単価を入力させる。
6. 全て確定したら、`ContainerLockManager.create(owner, {対象ブロック})`でロックを作成し、`shops`テーブルにレコードを挿入、作成費を徴収し、チェスト上に浮遊表示（ItemDisplay + TextDisplay）を生成する。

チャット入力の捕捉は、`TpaCore`/`KikoriManager`と同様に、プレイヤーUUIDをキーにした保留状態をメモリ上（`ShopListener`内のMapなど）に持たせて`AsyncChatEvent`で拾う方式とする。捕捉中のメッセージは通常のチャットとしてブロードキャストしない。

### ② 取引（購入者・売却者側の操作）

- 既存ショップチェストへの**右クリック（Sneakなし）**で、確認GUI（`gui/ShopTransactionGui`）を開く。
- 確認GUI内でのみ数量を調整でき、実際の在庫・資金・残高チェックと更新は**確定ボタンを押した瞬間にのみ**行う。GUIを個数調整だけして閉じても何も起こらない。
- Sneak+右クリックによる「まとめ買い/売り」のショートカットは廃止し、通常の右クリックのみで確認GUIに統一する。ただし、**自分が所有するショップ**への右クリックは取引ではなく管理メニュー（後述）を開く。

#### 確認GUIの数量調整仕様

- 中央のプレビュースロットに、選択中の個数を表すアイテムを表示する。表示スタック数は`min(選択個数, アイテムの最大スタック数)`。
- 選択個数がアイテムの最大スタック数を超えている場合、プレビューアイテムに**エンチャントの光沢（グリント）**を付与し、「1スタックを超える数量を選択中」であることを視覚的に示す。
- ツールチップ（lore）には常に正確な数量・単価・合計金額を明記する（例:「数量: 128個」「単価: ¥500」「合計: ¥64,000」）。
- 左右の調整ボタン：
  - 選択個数がアイテムの最大スタック数**未満**の間は「-1個/+1個」単位で動く。
  - 選択個数がアイテムの最大スタック数に**到達した以降**は「-1スタック/+1スタック」単位に切り替わる。ボタンの表示・ツールチップも動的に変わる。
  - 上限は「アイテムの最大スタック数 × 16」（通常アイテムは64×16=1024個、非スタック可能アイテムは1×16=16個）。
- 確定/キャンセルボタンで締める。

### ③ 管理メニュー（オーナー専用）

自分が所有するショップチェストへの**Sneak+右クリック**で開く（`gui/ShopManageGui`）。既存の未使用フレームワーク`gui/Gui`を初めて実戦投入する。

- **在庫を入れる**: GUI内の専用スロットに手持ちアイテムをドラッグ＆ドロップし、確定で仮想在庫へ加算する。
- **在庫を引き出す**: 仮想在庫からインベントリへ戻す。
- **資金を入金/引き出す**（SELLショップのみ）: ボタン押下でチャットに金額入力を求める（作成時の価格入力と同じ捕捉方式）。
- **ショップを削除**: `/lock`のロック解除、残在庫のインベントリへの返却（満杯ならドロップ）、残資金プールのVault残高への返金、浮遊表示Entityの削除、`shops`テーブルのレコード削除を行う。チェスト自体は破壊せず、ロックなしの空きチェストとして残す。

### ④ 保護

自前の破壊防止ロジックは実装せず、既存の`ContainerLockManager`/`ContainerLockListener`にフルで委譲する。

- ショップ作成時に対象チェストを`ContainerLockManager.create()`でロックすることで、以下が無料で付与される。
  - 非オーナーによる破壊のブロック（`canManage`チェック）
  - ホッパーによる搬入出のブロック（`InventoryMoveItemEvent`）
  - TNT/爆発耐性（`blockList().removeIf(isLocked)`）
  - ピストンによる押し引きのブロック
  - 非オーナーによる右クリックでのインベントリオープンのブロック
- `ShopListener`は、ロックされたブロックが**正当に**（オーナー本人、または管理者のbypassモードで）破壊された後の後始末役に徹する。`BlockBreakEvent`を`ContainerLockListener`より低い優先度（`MONITOR`など、実際に破壊が確定した後）で監視し、対象がショップだった場合に上記「ショップを削除」と同じ後始末処理を行う。

### ⑤ ラージチェスト対策

- 設置対象アイテムの制約により、ショップ化できるのは`Material.CHEST`の**シングルチェストのみ**。
- ショップ化した時点で`Chest.Type != SINGLE`なら作成を拒否する。
- ショップ化後、隣接マスへのチェスト設置（`BlockPlaceEvent`）を監視し、それがショップチェストとの連結（ラージチェスト化）につながる場合は、**設置者がショップのオーナーであっても**問答無用でキャンセルする。既存の`ContainerLockListener#joinLockedChest`は「オーナーなら連結OK」という挙動だが、ショップチェストに限りこれを上書きする形でイベントをキャンセルする。

## データモデル

新規テーブル`shops`を`DatabaseManager.createTableIfNotExists`で作成する（`land_*`系テーブルと同じ作法）。

```
id                 INTEGER PRIMARY KEY AUTOINCREMENT
owner_uuid         TEXT NOT NULL
world              TEXT NOT NULL
x, y, z            INTEGER NOT NULL
mode               TEXT NOT NULL         -- 'BUY' or 'SELL'
item_data          TEXT NOT NULL         -- ItemStackをBase64シリアライズ（NBT/エンチャ込み、1個分）
price              REAL NOT NULL         -- 単価
stock              INTEGER NOT NULL DEFAULT 0   -- 仮想在庫
funds              REAL NOT NULL DEFAULT 0      -- SELLショップ専用の資金プール
display_item_uuid  TEXT                  -- 浮遊ItemDisplayのEntity UUID
display_text_uuid  TEXT                  -- 浮遊TextDisplayのEntity UUID
created_at         INTEGER NOT NULL

UNIQUE (world, x, y, z)
```

`ShopManager`は起動時に全件をロードし、`BlockKey`（world, x, y, z）をキーにしたメモリキャッシュを持つ。`ContainerLockManager`/`MuteManager`と同様、ホットパス（ブロック操作イベント）で毎回SQLiteに問い合わせない設計とする。

### BUYショップとSELLショップの資金の流れ

- **BUYショップ**（プレイヤーが購入する）: 購入者の残高からオーナーの残高へ直接送金し、仮想在庫を減らす。資金プールは使わない。
- **SELLショップ**（プレイヤーが売却する）: オーナーが事前にチャージした資金プール（`funds`）から売却者へ支払い、仮想在庫を増やす。資金プールが不足していれば取引は失敗する（オーナーへの入金依頼が必要）。

## 新規クラス

- `managers/ShopManager` — キャッシュ管理、CRUD、在庫/資金の増減、浮遊表示Entityの生成・削除
- `listeners/ShopListener` — 設置トリガー（Sneak+右クリック）、チャット入力捕捉（BUY/SELL選択・価格入力・資金入出金額入力）、ラージチェスト化防止（`BlockPlaceEvent`）、破壊後の後始末（`BlockBreakEvent`、`ContainerLockListener`より低優先度）
- `gui/ShopTransactionGui`（`gui/Gui`継承） — 取引確認GUI（個数調整・プレビュー・確定/キャンセル）
- `gui/ShopManageGui`（`gui/Gui`継承） — オーナー管理メニュー（在庫入出金・資金入出金・削除）
- `commands/ShopCommand` — `/shop list`（自分のショップ一覧）、`/shop remove`（注視先のショップを削除、チェストは破壊しない）、`/shop info`（注視先のショップ詳細）

## 設定・メッセージ

`config.yml`に`shop.*`セクションを追加する。

- `shop.max-per-player`（デフォルト10）
- `shop.creation-cost`（デフォルト500）
- `shop.display.*`（浮遊表示のオフセット・スケール等）

`messages.yml`に`shop.*`セクションを追加し、既存の「プレイヤー向け文言は全てconfig駆動」方針に従って全メッセージを定義する。

## エラーハンドリング

- **作成時**: 対象が`minecraft:chest`以外／連結チェスト／既に他人にロック済み／上限到達／作成費不足 — それぞれ専用メッセージで拒否し、DBには一切触れない。
- **取引確定時**: 在庫不足／資金プール不足／購入者の残高不足 — GUI内でエラー表示し、`DatabaseManager.transaction()`でアトミックに扱うためDBは変更しない。
- **破壊時**: 非オーナーによる破壊は`ContainerLockListener`側で既にブロックされるため、`ShopListener`は「オーナー本人、または管理者のbypassモードによる正当な破壊」のみを検知して後始末する。

## テスト方針

本リポジトリには自動テストが存在しない（`src/test`なし）ため、既存方針に従い`./gradlew runServer`での手動確認とする。

- BUYショップ・SELLショップそれぞれの作成
- 1個〜スタック超の数量での売買、確認GUIの個数調整挙動
- 在庫切れ・資金プール不足・残高不足時のエラー表示
- オーナーによる破壊時の在庫/資金返金
- 非オーナーによる破壊のブロック
- ホッパー・TNT・ピストンに対する耐性（`/lock`委譲の確認）
- 連結チェスト化の拒否（作成時・作成後の隣接設置時）
- `/shop list`・`/shop remove`・`/shop info`の動作
