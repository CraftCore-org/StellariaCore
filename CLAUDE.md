# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

StellariaCore is a PaperMC (Minecraft 1.21) plugin written in Java 21, built with Gradle (Kotlin DSL). It provides a small set of gameplay features for the "Stellaria" server: TPA-style teleport requests, a SQLite-backed economy hooked into Vault, join/quit message formatting, and a custom tablist.

## Build & run

- `./gradlew build` — compiles, runs Shadow to produce the fat jar (`build/libs/StellariaCore-<version>.jar`, classifier disabled so it's the plain jar name), then copies it into `run/plugins/` for local testing.
- `./gradlew runServer` — launches a local Paper 1.21.11 test server (via the `run-paper` plugin) with the plugin loaded from `run/plugins/`.
- There are no automated tests in this repo (no `src/test`, no test task configured).
- CI (`.github/workflows/build.yml`) just runs `./gradlew build --no-daemon --refresh-dependencies` on push/PR to `main`.
- On every push to `main` that isn't itself a version-bump commit, `.github/workflows/version-bump.yml` bumps the patch/minor/major version in `build.gradle.kts` based on the merged PR's `bump:major`/`bump:minor` label (default patch), commits with `[ci-version-bump]`, tags, builds, and publishes a GitHub Release — don't hand-edit the `version` in `build.gradle.kts` on `main`.

Runtime dependencies (`compileOnly`, expected to be provided by the server): Paper API, Citizens, PacketEvents, VaultUnlockedAPI, PlaceholderAPI, Lombok. The only bundled/shaded dependency is `sqlite-jdbc`. `plugin.yml`'s `version` is templated from the Gradle `version` at `processResources` time — don't edit the version there directly.

## Architecture

**Wiring is manual, all in `StellariaCore#onEnable`** — there's no DI container. Order matters: construct `ConfigManager` right after `saveDefaultConfig()` → `DatabaseManager.connect()` → create the `players` table → construct `EconomyManager` → register it with Vault's `ServicesManager` (skipped with a warning if Vault isn't present) → register listeners (including `PlayerQuitListener`) → register the `TpaCore` executor for all six tpa commands → register `ReloadCommand` for `/stellariareload` → print the console banner. `onDisable` just closes the DB connection.

**`managers/ConfigManager` is a multi-file YAML registry, not just a `config.yml` wrapper.** Instantiated once in `onEnable` (unlike `DatabaseManager`, it holds real instance state — a `plugin` reference) and exposed via `StellariaCore#getConfigManager()`. It no longer touches Bukkit's built-in `getConfig()`/`saveDefaultConfig()`/`reloadConfig()` at all — `StellariaCore#onEnable` calls `configManager.register("config.yml")` and `register("messages.yml")`, each backed by its own `ConfigFile` (copies the jar's bundled default into the data folder on first run, ported from orelia-serverutil's `ConfigManager`/`ConfigFile`, minus its config-migration feature). `getString`/`getInt` always read `config.yml` (server/economy settings); `getMessage(path, OfflinePlayer)` always reads `messages.yml` and runs it through `FormatUtil.text(...)` — `%player%` substitution, PlaceholderAPI, and color codes all applied in one call. `/stellariareload` calls `ConfigManager.reload()`, which reloads every registered file. Every class that sends a config-driven message (`TpaCore`, `PlayerJoinListener`, `PlayerQuitListener`) goes through `ConfigManager`, never `plugin.getConfig()` directly — a past merge briefly reintroduced direct `plugin.getConfig()` calls in `TpaCore`, so watch for that pattern creeping back in. There is deliberately no separate `MessageManager` class — `ConfigManager.getMessage()` covers it, since `messages.yml` is just another registered file.

**Persistence is a single static SQLite wrapper, not a DAO layer.** `managers/DatabaseManager` holds the one `Connection` as a static field and exposes generic `query`/`queryOne`/`insert`/`update`/`execute` (+ `Async` variants that hop off-thread via `Bukkit.getAsyncScheduler()`) plus a `transaction()` helper. Every feature that touches the DB (currently `EconomyManager`, `PlayerJoinListener`) calls these statics directly with raw table/column names rather than going through a repository — there's one table, `players` (`uuid`, `name`, `coins`). Despite living in `managers/`, it is fully static (private constructor, no instance state but the static `Connection`) — unlike `EconomyManager` below.

**Naming convention: `utils/` = stateless static helpers, `managers/` = longer-lived components with more responsibility (not strictly "instantiated").** Everything in `utils/` (`ColorUtil`, `ConsoleUtil`, `FormatUtil`) has a private constructor and only static methods, same as `DatabaseManager`. `managers/EconomyManager` is instantiated once in `onEnable` and holds a `plugin` reference; it extends Vault's `AbstractEconomy` and implements balance ops by reading/writing `DatabaseManager` directly (no caching). `managers/PluginManager` is an unused singleton stub (`initialize()` is empty, nothing calls it) — the commented-out `PluginManager.getInstance().initialize()` line in `StellariaCore` reflects that. So the `utils`/`managers` split currently tracks "how central/stateful is this to the plugin's domain" more than "static vs. instantiated" — don't assume everything under `managers/` is instance-based.

**Two listener classes overlap on player join/quit without coordinating:** `PlayerJoinListener` (DB record creation + join message) and `PlayerListener` (tablist refresh on join + TPA request cleanup on quit) both fire on the same events; `PlayerQuitListener` (quit message) is a third one covering the same quit event. All three are registered in `onEnable`, but this split-by-concern-across-separate-listener-classes pattern means a new join/quit behavior could plausibly go in any of the three — check all of them before assuming one is authoritative.

**Text formatting has two parallel color pipelines.** `ColorUtil` supports legacy `&` codes, `&#RRGGBB` hex, and a custom `&%<char>` palette (defined in `ColorUtil.CUSTOM_COLORS`); `FormatUtil` wraps it and additionally does `%player%` substitution and PlaceholderAPI expansion (`FormatUtil.text(...)`, normally reached via `ConfigManager.getMessage(...)`, is what every config-driven message goes through). `config.yml` is written entirely in the `&%<char>` custom palette (not raw `§` codes, not plain `&a`-style legacy codes) — format codes like bold/reset (`&l`, `&r`) stay as plain legacy codes since they're not colors and have no `&%` entry. `utils/Utils.colorize` is an older, separate implementation of roughly the same hex-color logic and is not called from anywhere — don't extend it, use `ColorUtil`/`FormatUtil`.

**`TpaCore` is a single `CommandExecutor` for all six tpa commands** (`tpa`, `tpaccept`, `tpdeny`, `tphere`, `tphaccept`, `tphdeny`), dispatching on `command.getName()` inside one `onCommand`. It takes a `StellariaCore plugin` in its constructor to reach `ConfigManager` for every message under `tpa.*` in `messages.yml` — every user-facing string is config-driven, none are hardcoded. Pending requests live in two static `Map<UUID, List<UUID>>` fields (in-memory only, cleared per-player via `resetPlayerTeleportRequests` on quit) — there's no persistence or timeout for requests.

**All user-facing text lives in `messages.yml`, not `config.yml`.** `join`, `quit`, and `tpa.*` are top-level keys in `messages.yml` (not nested under a `messages:` key — the whole file is messages). `config.yml` only holds server/economy settings, two of which are marked `!NOTE: 未実装` (not yet implemented) and read from nowhere in the code: `server.prefix` and `economy.default-balance`.

**`EconomyManager.format()` and the `%money%` placeholder go through `utils/MoneyFormat`**, which abbreviates large amounts into 万/億/兆 (e.g. `15000` → `"1.5万"`) rather than showing the raw integer — ported from orelia-serverutil's `MoneyFormat` (which uses English k/m/b/t suffixes instead).

**Multi-line hover tooltips are built through `PlaceholderManager.resolveLines(List<String>, Player)`**, shared by both `ChatListener` (`chat.tooltip.lines` in `config.yml`, hovering the sender's name) and `TpaCore` (`tpa.tpa_accept_tooltip`/`tpa_deny_tooltip` in `messages.yml`, hovering the accept/deny buttons via a `TpaCore#button(...)` helper reused by both `tpa` and `tphere`). It resolves each line individually (so per-line `%token%`s work) and joins them with `Component.newline()`; returns `null` for an empty/missing list so callers can skip attaching a hover event entirely.

**Chat mentions and URLs are both "scan plain text, splice in special Components" passes, layered one after another.** `MentionService.highlight(...)` finds `@name`/`@all` first; whatever text is left over (not a mention) goes through `utils/UrlHighlighter.highlight(...)`, which finds `http(s)://` URLs and turns them into blue-underlined `ClickEvent.openUrl(...)` links (excluding trailing Japanese punctuation/closing brackets from the match so a URL followed by `。` or `)` doesn't swallow it). Both passes respect the same `colorize` flag (whether the sender is allowed to use `&`-codes in their own message, per `chat.color-codes.*`).

**Scoreboard sidebar, tab-list header/footer/value, and the below-name health display are all config-driven templates resolved through `managers/PlaceholderManager`.** `PlaceholderManager.resolve(template, Player)` replaces built-in `%token%`s (`%online%`, `%max_online%`, `%tps%`, `%ping%`, `%world%`, `%server%`, `%x%`/`%y%`/`%z%`/`%location%`, `%date%`, `%time%`, `%money%`, `%health%`/`%max_health%` — the latter two are hearts, i.e. raw HP÷2, matching vanilla's 10-heart display, not the raw 0–20 HP scale) and then delegates to `FormatUtil.text(...)` for `%player%`/PlaceholderAPI/color — so a `%papi_...%` token dropped into any of these config templates resolves normally as long as that PAPI expansion is installed. `ScoreboardManager`, `TabListManager`, and `BelownameManager` (all in `managers/`, all instantiated in `onEnable`, all ticked via `Bukkit.getGlobalRegionScheduler().runAtFixedRate(...)` at their own `*.update-interval-ticks`) render onto a shared per-player personal `Scoreboard` via `utils/BoardUtil.ensurePersonalBoard(...)` so they don't clobber each other's objectives/teams — this is the same layering `orelia-serverutil` uses. Unlike orelia's versions, none of these three publish a cross-plugin `ServicesManager` extension point (no `XApi`/`XValueProvider`) — content is config templates only, since nothing else currently needs to plug values in. `TabListManager` replaced the old standalone `TabList` class (static, join-triggered-only header/footer with no live tokens) entirely; `/stellariareload` calls `StellariaCore#reloadFeatureManagers()` (after `ConfigManager#reload()`) to push fresh config values into all three without a restart.
