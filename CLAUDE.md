# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

StellariaCore is a PaperMC (Minecraft 1.21) plugin written in Java 21, built with Gradle (Kotlin DSL). It provides the gameplay features for the "Stellaria" server: TPA-style teleport requests, homes/warps, a SQLite-backed economy hooked into Vault, chat (mentions/URLs/color codes) with a tiered mute system, private messages, join/quit formatting, a scoreboard/tablist/belowname/nametag/action-bar HUD stack driven by LuckPerms ranks, AFK tracking, playtime/ranking, elevators, and a "kikori" (lumberjack) tree-felling minigame.

## Build & run

- `./gradlew build` — compiles, runs Shadow to produce the fat jar (`build/libs/StellariaCore-<version>.jar`, classifier disabled so it's the plain jar name), then copies it into `run/plugins/` for local testing.
- The build is now a multi-project build: `enchant-keys` (shared enchantment key constants, shaded into both jars) and `stellaria-enchants` (a separate Paper plugin with `paper-plugin.yml` + bootstrapper that only registers the custom enchantments). `./gradlew build` produces and copies both `StellariaCore-<version>.jar` and `StellariaEnchants-<version>.jar` into `run/plugins/`, and the release workflow attaches both. Because of this, `./gradlew test --tests X` applies the filter to every subproject and fails with "No tests found" — use `./gradlew :test --tests X` for root-project tests.
- `./gradlew runServer` — launches a local Paper 1.21.11 test server (via the `run-paper` plugin) with the plugin loaded from `run/plugins/`.
- There are no automated tests in this repo (no `src/test`, no test task configured).
- CI (`.github/workflows/build.yml`) just runs `./gradlew build --no-daemon --refresh-dependencies` on push/PR to `main`.
- On every push to `main` that isn't itself a version-bump commit, `.github/workflows/version-bump.yml` bumps the patch/minor/major version in `build.gradle.kts` based on the merged PR's `bump:major`/`bump:minor` label (default patch), commits with `[ci-version-bump]`, tags, builds, and publishes a GitHub Release — don't hand-edit the `version` in `build.gradle.kts` on `main`.

Runtime dependencies (`compileOnly`, expected to be provided by the server): Paper API, Citizens, PacketEvents, VaultUnlockedAPI, PlaceholderAPI, LuckPerms API, Lombok (`softdepend` in `plugin.yml` — `RankManager` degrades to "no ranks" if it's missing, nothing else touches it). The only bundled/shaded dependency is `sqlite-jdbc`. `plugin.yml`'s `version` is templated from the Gradle `version` at `processResources` time — don't edit the version there directly.

## Production deployment notice

This server is live in production. Whenever a change touches the database schema (new table, new/changed column, `addColumnIfNotExists`, anything under `managers/DatabaseManager`'s table-creation block in `StellariaCore#onEnable`) or a default/structural change to `config.yml` or `messages.yml` (new keys, renamed keys, changed defaults that affect existing installs), call it out explicitly in your response to the user as its own callout before wrapping up — don't bury it in a general summary. Say what changed and why it needs attention (e.g. "既存のconfig.ymlには手動で追記が必要" or "既存のDBには自動でマイグレーションされるが再起動が必要" etc.), so it can be checked before/around a deploy.

## Architecture

**Wiring is manual, all in `StellariaCore#onEnable`** — there's no DI container, and there are now ~20 manager fields plus ~30 commands wired by hand. Order matters: construct `ConfigManager` → `register("config.yml")`/`register("messages.yml")` → `DatabaseManager.connect()` → create every table (`players`, `mutes`, `player_stats`, `homes`, `warps`) and run any `addColumnIfNotExists` migrations → construct the per-feature managers (`AfkManager`, `PlaytimeManager`, `RankManager`, `HomeManager`, `WarpManager`, `KikoriManager`, `MuteManager` + `loadAll()`, `PrivateMessageManager`, `ActionBarManager`) → construct `EconomyManager` and register it with Vault's `ServicesManager` (skipped with a warning if Vault isn't present) → register listeners → construct `PlaceholderManager` and the HUD managers (`ScoreboardManager`, `TabListManager`, `BelownameManager`, `NametagManager`) and start their `runAtFixedRate` ticks → register every command executor/tab-completer → start `AutoBroadcastManager` → print the console banner. `onDisable` just closes the DB connection. `StellariaCore#reloadFeatureManagers()` (called by `ReloadCommand` after `ConfigManager#reload()`) is the one place that pushes fresh config values into the HUD managers + `AutoBroadcastManager`/`RankManager` without a restart — a new manager with reloadable config needs a line added here too.

**`managers/ConfigManager` is a multi-file YAML registry, not just a `config.yml` wrapper.** Instantiated once in `onEnable` (unlike `DatabaseManager`, it holds real instance state — a `plugin` reference) and exposed via `StellariaCore#getConfigManager()`. It no longer touches Bukkit's built-in `getConfig()`/`saveDefaultConfig()`/`reloadConfig()` at all — each registered file is backed by its own `ConfigFile` (copies the jar's bundled default into the data folder on first run, ported from orelia-serverutil's `ConfigManager`/`ConfigFile`, minus its config-migration feature). `getString`/`getInt`/`getBoolean`/`getDouble`/`getStringList`/`getMapList` always read `config.yml`; `getMessage(path, OfflinePlayer)` reads `messages.yml` and runs it through `FormatUtil.text(...)` (`%player%` substitution + PlaceholderAPI + color codes in one call), while `getRawMessage`/`getMessageList` return `messages.yml` values unformatted for callers that need to splice in their own `Component`s (e.g. `BroadcastCommand`) or resolve per-line via `PlaceholderManager`. Every getter has an `ignoreWarn` overload; without it, a missing key logs a one-time-per-key warning (reset by `reload()`) instead of failing silently forever. `/stellariareload` calls `ConfigManager.reload()`, which reloads every registered file. Every class that sends a config-driven message goes through `ConfigManager`, never `plugin.getConfig()` directly — a past merge briefly reintroduced direct `plugin.getConfig()` calls in `TpaCore`, so watch for that pattern creeping back in. There is deliberately no separate `MessageManager` class — `ConfigManager.getMessage()` covers it.

**Persistence is a single static SQLite wrapper, not a DAO layer.** `managers/DatabaseManager` holds the one `Connection` as a static field and exposes generic `query`/`queryOne`/`insert`/`update`/`execute`/`exists` (+ `Async` variants that hop off-thread via `Bukkit.getAsyncScheduler()`) plus a `transaction()` helper and `addColumnIfNotExists(table, columnDef)` for adding a column to an existing table without a migration framework (used to bolt `kikori_unlocked` onto `players` after the fact). Every feature that touches the DB calls these statics directly with raw table/column names rather than going through a repository. Tables: `players` (`uuid`, `name`, `coins`, `kikori_unlocked`, `hide_balance`, `hide_stats_ranking`), `player_stat_snapshots` (`uuid`+`stat_key` composite key, `value`, `updated_at`), `player_counters` (`uuid`+`counter_key`, `value`), `player_counter_members` (`uuid`+`counter_key`+`member`), `player_advancements` (`uuid`+`advancement_id`, `completed_at` — 0 means revoked, `reward_paid`, `reward_amount`), `player_login_days` (`uuid`+`day`, Japan-time `yyyy-MM-dd`), `mutes` (`uuid`, `level`, `expires_at`, `reason`, `muted_by`, `muted_at`), `player_stats` (`uuid`, `last_logout`, `playtime_seconds`), `homes` (`uuid`+`name` composite key, world/x/y/z/yaw/pitch), `warps` (`name` primary key, `owner_uuid`, world/x/y/z/yaw/pitch). Despite living in `managers/`, `DatabaseManager` is fully static (private constructor, no instance state but the static `Connection`) — unlike `EconomyManager`/`MuteManager`/etc. below.

**Naming convention: `utils/` = stateless static helpers, `managers/` = longer-lived components with more responsibility (not strictly "instantiated").** Everything in `utils/` (`ColorUtil`, `ConsoleUtil`, `FormatUtil`, `MoneyFormat`, `TreeUtil`, `TabCompleteUtil`, `DurationParser`, `TeleportSafetyUtil`, `BoardUtil`, `UrlHighlighter`, `ParticleUtil`) has a private constructor and only static methods, same as `DatabaseManager`. Most of `managers/` is instantiated once in `onEnable` and holds a `plugin` reference (`EconomyManager` extends Vault's `AbstractEconomy` and reads/writes `DatabaseManager` directly with no caching; `MuteManager`/`RankManager`/`HomeManager`/etc. follow the same shape). `managers/PluginManager` is an unused singleton stub (`initialize()` is empty, nothing calls it) — the commented-out `PluginManager.getInstance().initialize()` line in `StellariaCore` reflects that. So the `utils`/`managers` split tracks "how central/stateful is this to the plugin's domain" more than "static vs. instantiated" — don't assume everything under `managers/` is instance-based.

**Three listener classes split player join/quit handling by concern, without a shared base:** `PlayerJoinListener` (DB record creation + join message), `PlayerQuitListener` (quit message), and `PlayerListener` (AFK activity tracking on move/interact, elevator jump/sneak triggers, and — on quit — clearing `TpaCore`'s pending requests plus `AfkManager`/`ActionBarManager`/`KikoriManager` per-player state). All three are registered in `onEnable` and all three (well, two) fire on `PlayerQuitEvent`. A new join/quit behavior — especially "clean up this manager's per-player state on quit" — most plausibly belongs in `PlayerListener` next to the existing cleanup calls, but check all three before assuming which one is authoritative for a given concern.

**Text formatting has two parallel color pipelines.** `ColorUtil` supports legacy `&` codes, `&#RRGGBB` hex, and a custom `&%<char>` palette (defined in `ColorUtil.CUSTOM_COLORS`); `FormatUtil` wraps it and additionally does `%player%` substitution and PlaceholderAPI expansion (`FormatUtil.text(...)`, normally reached via `ConfigManager.getMessage(...)`, is what every config-driven message goes through). `config.yml`/`messages.yml` are written entirely in the `&%<char>` custom palette (not raw `§` codes, not plain `&a`-style legacy codes) — format codes like bold/reset (`&l`, `&r`) stay as plain legacy codes since they're not colors and have no `&%` entry. `utils/Utils.colorize` is an older, separate implementation of roughly the same hex-color logic and is not called from anywhere — don't extend it, use `ColorUtil`/`FormatUtil`.

**`TpaCore` is a single `CommandExecutor` for all six tpa commands** (`tpa`, `tpaccept`, `tpdeny`, `tphere`, `tphaccept`, `tphdeny`), dispatching on `command.getName()` inside one `onCommand`. It takes a `StellariaCore plugin` in its constructor to reach `ConfigManager` for every message under `tpa.*` in `messages.yml` — every user-facing string is config-driven, none are hardcoded. Pending requests live in two static `Map<UUID, List<UUID>>` fields (in-memory only, cleared per-player via `resetPlayerTeleportRequests` on quit) — there's no persistence or timeout for requests. This same "in-memory only, cleared on quit" shape recurs in `KikoriManager` (toggle state + pending pass) and `AfkManager`.

**`HomeManager`/`WarpManager` persist named locations, and share a teleport-safety confirmation flow via `utils/TeleportSafetyUtil`.** Homes are per-player (`homes` table, `uuid`+`name` PK); warps are server-wide but track `owner_uuid` for permission checks. Both `HomeCommand` and `WarpCommand` route the actual teleport through `TeleportSafetyUtil`, which checks the destination for obvious hazards and, if unsafe, requires the player to re-run the same command within ~10 seconds to force the teleport anyway — but the pending-confirmation state itself (`PendingConfirm`) is kept by each command class in its own static map, not by `TeleportSafetyUtil`, so `HomeCommand` and `WarpCommand` each pass their map in as an argument rather than sharing one.

**`MuteManager` is a tiered, scoped mute system: DB-backed, but judged entirely from an in-memory cache.** Unlike `EconomyManager` (no caching) or `HomeManager`/`WarpManager` (query-on-demand), `MuteManager.loadAll()` reads the whole `mutes` table into a `Map<UUID, MuteRecord>` once in `onEnable`, because mute checks fire on every chat message/PM/command. `MuteScope` (`CHAT`=1, `PM`=2, `COMMAND`=3) defines an ascending severity ladder — a mute's `level` restricts every scope whose `requiredLevel` is `<= level`, so `level=1` blocks chat only, `level=3` blocks chat+PM+commands. `getRecord()` lazily expires and self-deletes (cache + async DB delete) once `expires_at` has passed; `expiresAt < 0` means permanent. `MuteCommandBlockListener` is what actually enforces the `COMMAND` scope by cancelling command execution.

**`RankManager` is the only class that touches the LuckPerms API.** It reads a player's LuckPerms group membership and converts it into a `RankInfo` (color, tablist tag, display name) using the `rank.groups` list in `config.yml`; `TabListManager` and `NametagManager` both consume `RankInfo` from here rather than calling LuckPerms themselves. If the `LuckPerms` plugin isn't present, `RankManager` degrades gracefully (checked via `Bukkit.getPluginManager().getPlugin("LuckPerms") == null`) rather than throwing.

**All user-facing text lives in `messages.yml`; server/feature behavior settings live in `config.yml`.** Both files have grown a top-level key per feature area (`messages.yml`: `join`, `quit`, `tpa`, `afk`, `heal`, `broadcast`, `mute`, `msg`, `chat`, `mention`, `pay`, `eco`, `balance`, `colors`, `discord`, `playtime`, `seen`, `ranking`, `scoreboard`, `home`, `warp`, `kikori`; `config.yml`: `server`, `discord`, `rank`, `economy`, `home`, `warp`, `ranking`, `first-join-kit`, `action-bar`, `scoreboard`, `tablist`, `belowname`, `nametag`, `afk`, `chat`, `message`, `mute`, `tpa`, `teleport-effect`, `join-effect`, `mention`, `broadcast`, `elevator`, `kikori`) — the split itself hasn't changed from "config.yml = not shown directly to players, messages.yml = is." The one exception is `advancements.yml`: advancement titles/descriptions live next to their definitions there, so one advancement isn't split across two files (behavior settings such as rewards still go in `config.yml` `advancements.*`).

**`/ranking` reads vanilla statistics from `player_stat_snapshots`, never live from Bukkit.** `managers/StatSnapshotManager` writes each player's values for the 11 keys in `utils/StatDefinitions` (mob kills, deaths, blocks mined/placed summed over every material, distance summed over the movement stats, etc.) on quit, every `ranking.snapshot-interval-minutes`, and synchronously in `onDisable`. On enable, players with no snapshot rows are backfilled asynchronously by parsing the main world's `stats/<uuid>.json` with `utils/StatFileParser` — `OfflinePlayer#getStatistic` re-reads the file on every call, so it is unusable for per-material sums. Which keys `/ranking` exposes comes from `config.yml` `ranking.stats`; display names are `messages.yml` `ranking.stat_names.*`. `players.hide_stats_ranking` (toggled in `SettingsGui`) hides a player from the stat and playtime rankings, while `money` still uses only `hide_balance`. `/ranking advancements` counts each player's completed custom advancements (`player_advancements` rows with `completed_at > 0`, hidden ones included) and follows `hide_stats_ranking`. `/ranking earned` (lifetime money earned, counted from its release) reads the `economy.earned` row of `player_counters` via `managers/EarningsStore` and also hides `hide_balance` players; income sites call `EconomyManager#recordEarning` after the deposit commits (mining/fishing income, shop sales and sell-to-shop, `/pay` received, `/eco give`, vote and advancement rewards, home/warp/land deletion refunds) — rollback refunds and shop-fund withdrawals/returns deliberately do not, since they are the player's own money coming back and would let fund in/out loops inflate the ranking. kikori/mine/excavation breaks already count toward `mined` because they all go through `player.breakBlock()`.

**Custom advancements are DB-first; vanilla advancements are only the display.** `advancements.yml` defines tabs and advancements (`utils/AdvancementDefinitions` validates them and drops broken entries — plus anything whose `parent`/`all_of` points at a dropped one — with warnings). `AdvancementRegistrar` registers them in memory via the deprecated `Bukkit.getUnsafe().loadAdvancement` under `stellaria:<tab>/<id>` (tab roots are `stellaria:<tab>/root`, auto-granted on join) on every enable and again on `ServerResourcesReloadedEvent` — Paper 1.21.11 writes those JSONs to `datapacks/bukkit/data/<ns>/advancements/` (plural) but vanilla 1.21+ only reads `advancement/`, so registrations never survive a restart or `/minecraft:reload`, and `removeAdvancement` only deletes the file without unloading anything. Feature code only calls `AdvancementManager#increment(player, key, n)` / `addDistinct(player, key, member)`; which advancements watch a key is decided from the definitions (`utils/AdvancementRules`). Completion, the reward (`EconomyManager`, paid once per advancement via `reward_paid`, even across admin revoke/re-grant) and `all_of`/`completed` chaining happen in `AdvancementManager#complete`; on join the vanilla state is re-synced from the DB without paying rewards (vanilla-only grants are revoked). `stat` triggers are evaluated on join and whenever `StatSnapshotManager` snapshots a player. Built-in counter: `join.count`. Every counter key and where it is recorded is listed in `docs/superpowers/specs/2026-09-26-advancements-content-design.md` §3 (e.g. `pay.*` in `PayCommand`, `shop.*` in `ShopManager#recordPurchase`, `rail.*` in `RailManager#recordArrival`, `kikori.trees` on felling completion, `tour.commands` via a `PlayerCommandPreprocessEvent` listener in `AdvancementManager`). The recording API — `event(uuid, key)`, `addToCounter(uuid, key, n)`, `addDistinct(uuid, key, member)` and the `Player` overloads — is safe to call for offline players and from async threads (chat, Votifier): the DB write happens immediately and the cache update/evaluation hops to the main thread. Anything "for other players" (shop sales, customers, warp usage) deliberately skips self-trades and one's own warps. Daily thresholds use Japan time: `shop.sales.<date>` rows in `player_counters` (read back synchronously so offline owners still get `shop.daily100k`), in-memory per-day chat counts, and `player_login_days` for streaks. Changes to `advancements.yml` take effect on restart, not `/stellariareload`.

**`EconomyManager.format()` and the `%money%` placeholder go through `utils/MoneyFormat`**, which abbreviates large amounts into 万/億/兆 (e.g. `15000` → `"1.5万"`) rather than showing the raw integer — ported from orelia-serverutil's `MoneyFormat` (which uses English k/m/b/t suffixes instead).

**Multi-line hover tooltips are built through `PlaceholderManager.resolveLines(List<String>, Player)`**, shared by `ChatListener` (`chat.tooltip.lines` in `config.yml`, hovering the sender's name) and `TpaCore` (`tpa.tpa_accept_tooltip`/`tpa_deny_tooltip` in `messages.yml`, hovering the accept/deny buttons via a `TpaCore#button(...)` helper reused by both `tpa` and `tphere`). It resolves each line individually (so per-line `%token%`s work) and joins them with `Component.newline()`; returns `null` for an empty/missing list so callers can skip attaching a hover event entirely.

**Chat mentions and URLs are both "scan plain text, splice in special Components" passes, layered one after another.** `MentionService.highlight(...)` finds `@name`/`@all` first; whatever text is left over (not a mention) goes through `utils/UrlHighlighter.highlight(...)`, which finds `http(s)://` URLs and turns them into blue-underlined `ClickEvent.openUrl(...)` links (excluding trailing Japanese punctuation/closing brackets from the match so a URL followed by `。` or `)` doesn't swallow it). Both passes respect the same `colorize` flag (whether the sender is allowed to use `&`-codes in their own message, per `chat.color-codes.*`). `DiscordCommand` reuses `UrlHighlighter` the same way to linkify just the invite URL inside its announcement message, without making the surrounding text clickable.

**Scoreboard sidebar, tab-list header/footer/value, below-name health, and the action bar are all config-driven templates resolved through `managers/PlaceholderManager`.** `PlaceholderManager.resolve(template, Player)` replaces built-in `%token%`s (`%afk%`, `%online%`, `%max_online%`, `%tps%`, `%ping%`, `%world%`, `%server%`, `%x%`/`%y%`/`%z%`/`%location%`, `%date%`, `%time%`, `%money%`, `%health%`/`%max_health%` — the latter two are hearts, i.e. raw HP÷2, matching vanilla's 10-heart display, not the raw 0–20 HP scale) and then delegates to `FormatUtil.text(...)` for `%player%`/PlaceholderAPI/color — so a `%papi_...%` token dropped into any of these config templates resolves normally as long as that PAPI expansion is installed. `ScoreboardManager`, `TabListManager`, `BelownameManager`, and `NametagManager` (all in `managers/`, all instantiated in `onEnable`, all ticked via `Bukkit.getGlobalRegionScheduler().runAtFixedRate(...)` at their own `*.update-interval-ticks`) render onto a shared per-player personal `Scoreboard` via `utils/BoardUtil.ensurePersonalBoard(...)` so they don't clobber each other's objectives/teams. `ActionBarManager` ticks the same way but works differently: because several features (the persistent config template, `KikoriManager`'s artificial-tree warning, etc.) may want the action bar at once, it composes multiple named "channels" per player into one line instead of each caller overwriting the last one's message directly; `flash(player, channel, component, ttlTicks)` is the helper for a temporary message that expires on its own. None of these publish a cross-plugin `ServicesManager` extension point (no `XApi`/`XValueProvider`) — content is config templates only. `/stellariareload` → `StellariaCore#reloadFeatureManagers()` pushes fresh config into all of these (plus `AutoBroadcastManager`/`RankManager`) without a restart.

**`AutoBroadcastManager` rotates through `broadcast.auto.*` messages in `config.yml`, one at a time, at a fixed interval**, resolving each message per-recipient through `PlaceholderManager` (so `%ping%`-style viewer-dependent tokens work) before sending. `restart()` (called from `reloadFeatureManagers()`) resets the rotation index so a reload doesn't leave it mid-list against a changed message set.

**`KikoriManager` implements the `/kikori` lumberjack minigame as a flood-fill over 26-connected log blocks, gated by a "did a player build this tree" check.** When an enabled player with an axe breaks a natural log (`KikoriListener`), `tryStartFelling` BFS/DFS-walks all 26-directional neighbors that are log blocks (`utils/TreeUtil`), stopping at `kikori.max-logs` and aborting the whole felling (turning the toggle off) if it hits a log tagged "artificial." Artificiality is tracked per-chunk via a `PersistentDataContainer` on the `Chunk` (`KikoriListener` tags on `BlockPlaceEvent`, untags on any `BlockBreakEvent` for that block) — coordinates are packed into a `long[]` (4 bits X, 4 bits Z, 9 bits Y) rather than stored as a list of `Location`s. Stripped logs are always treated as artificial regardless of tagging. `/kikori pass` grants a one-time bypass for a single artificial log encountered mid-tree. Collected logs (plus nearby non-persistent leaves within `kikori.leaf-radius`) are broken one block per tick via the *player's* entity scheduler (`player.getScheduler().runAtFixedRate`, same pattern as `TpaCore`'s countdown, so it self-cancels on disconnect); a `claimedBlocks` set gives cross-tree exclusivity so **one player can fell multiple trees concurrently** without double-processing a block, and a `suppressLeafDurability` flag is read by a `PlayerItemDamageEvent` hook to stop leaf-breaking from wearing down the axe (only log-breaking should). The feature itself is purchase-gated per player via the `players.kikori_unlocked` column (added post-hoc with `DatabaseManager.addColumnIfNotExists`), charged through `EconomyManager`.

**`gui/Gui` + `gui/GuiListener` are a generic inventory-GUI framework that nothing currently uses.** `GuiListener` is registered in `onEnable` and dispatches `InventoryClickEvent`/`InventoryCloseEvent` to any open inventory whose holder is a `Gui` subclass, but no command currently creates a `Gui` subclass — treat it as a prepared-but-dormant foundation (like `PluginManager`), not dead code to delete without checking whether a WIP branch depends on it.

**Custom enchantments are split across two plugins because registering them needs a Paper bootstrapper.** `stellaria-enchants` (Paper plugin) registers 11 enchantments via `RegistryEvents.ENCHANTMENT` and adds the non-treasure ones (`EnchantDefinitions.discoverable()`) to `#minecraft:in_enchanting_table`/`#minecraft:tradeable`; treasure ones (currently only `excavation`, the 3x3 pickaxe/shovel enchant targeting the custom `stellaria:enchantable/excavation` item tag) are obtainable only through StellariaCore's `AncientCityLootListener`, which adds a book to `minecraft:chests/ancient_city` loot at `custom-enchants.excavation.ancient-city-chance`; it has no runtime logic, and changing its definitions requires a full server restart. StellariaCore stays a `plugin.yml` plugin (migrating would break the ~96 `getCommand(...)` registrations) and implements the effects in `enchants/`, wired through `CustomEnchantModule` (`enable()` in `onEnable`, `reload()` in `reloadFeatureManagers()`). `CustomEnchantRegistry` looks the enchantments up by key at enable time and disables whatever is missing, so StellariaCore still boots without StellariaEnchants. Tunables live in `config.yml` `custom-enchants.*` (cached by `CustomEnchantConfig`), text in `messages.yml` `custom-enchants.*`. Pure logic (`EnchantMath`, `CooldownTracker`, `SaplingPlanner`, `AnglerStreakTracker`, `DoubleJumpRules`, `ExcavationRules`, `premium/PremiumCraftRules`) is unit-tested. Replant hooks `KikoriManager` through `setFellCompleteHandler(...)`, so it only works for players using the kikori feature. Premium crops (`enchants/premium/`) are vanilla crop materials tagged via PDC; `PremiumCropGuardListener` blocks every non-conversion use (recipes, crafter, planting, eating, cooking, composter, animals/villagers). Removing StellariaEnchants later strips these enchantments from players' items.
